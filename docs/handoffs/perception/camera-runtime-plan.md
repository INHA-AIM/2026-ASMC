- semantic의 뷰 선택과 달리 BEV·fusion·lane은 3뷰 고정이다. 상위 launch의 v6와 개별 lane launch의

여기에 구간별 준비·GPS 복귀를 독립 단계로 넣고, 공유 runtime은 측정상 필요할 때만 수행한다.

## 운용 원칙

### 음영구간과 GPS 복귀

음영구간에서는 카메라의 차량 기준 차선·주행가능영역으로 주행하고, 전역 위치·route station을
계속 추정하는 기능을 이번 카메라 계획의 선행 조건으로 두지 않는다. HD 패키지도 GPS 단절 때
현재 위치·차로·station을 무효화하고 역사값만 제공하며 위치를 외삽하지 않는다.

진입 전에 마지막 유효 HD 위치로 음영구간 접근을 확인해 모델을 준비한다. GPS가 끊기면
차선 추론은 반드시 유지한다. 아직 추론이 활성화되지 않은 예상 밖 GPS 손실에서도 모델 준비와
추론을 요청한다. 단절 순간에 처음 모델을 로드하는 방식은 정상 진입 경로로 사용하지 않는다.

GPS 손실은 어느 구간에서도 발생할 수 있으므로 손실 사실만으로 지도상의 특정 음영구간 ID를
새로 확정하지 않는다. 최초 GPS 부재·수신 오류와 정상 음영 진입은 진단에서 구분한다.
planning은 진입 시의 진행 방향·home/opposing 의미와 미션 상태를 보존할 수 있다.
이는 음영 안의 전역 위치를 계속 추정한다는 뜻이 아니다.

GPS가 복귀하면 새 source 관측의 유효성·freshness와 HD 차로·경로 재연결을 확인한 뒤
위치 기반 소비로 복귀한다. 새 header만으로 복구를 판단하거나 GPS 단 한 번의 수신으로
카메라 추론을 끄지 않는다. 복귀 확인과 제어 전환 정책은 3단계에서 planning과 검증한다.

### 필요한 시점의 10Hz 공급

TwinLite와 신호등의 목표는 구간 시작부터 안정적인 10Hz 추론이다. 이를 위해 모델은 시작 때
GPU에 로드·예열하고 유지하며, 필요 구간 전에 실제 영상으로 추론을 재개해 준비 여부를 확인한다.
구간 밖에서는 상시 추론 비용을 줄인다. dummy 예열 성공과 최신 영상 기반 준비 완료를 구분한다.

planning이 구간과 결과 사용 권한을 결정하고 카메라는 준비·추론·상태 보고를 수행한다.
`STANDBY → PREPARE → ACTIVE`를 기본 방향으로 삼되, 메시지·timeout·준비 거리와
실제 10Hz 수락 조건은 3단계 상세 계획에서 확정한다. 이전 제안의 3초·30m·5회 예열 등은
측정 전 확정 계약으로 이식하지 않는다.

### 입력 영상과 모델 최적화

신호등 ResNet18은 camera4, 현재 `/cam_extra/image_jpeg/compressed`를 사용한다.
TwinLite와 YOLO는 전방 영상을 공유할 수 있고 측방을 켜면 해당 영상도 공유할 수 있다.
같은 frame의 JPEG 디코딩은 공유 후보지만 모델별 resize·정규화·추론·후처리는 별도다.
camera4의 영상을 전방 영상과 같은 디코딩 결과로 대체하지 않는다.

공통 GPU의 스케줄링·전송·메모리는 전체적으로 측정하되 세 모델의 backend를 한 번에 바꾸지 않는다.
각 모델의 출력 동등성과 지연을 따로 검증한 후 조합 실행으로 경합을 확인한다.
신호등 구간과 음영구간의 실제 활성 조합, 준비 구간의 중첩, 개발용 세 모델 동시 실행을 각각 측정한다.

### YOLO 카메라 수와 주기

3카메라 YOLO는 대회 필수 조건이 아니다. 2단계에서는 기존 전방 경로를 보존하고,
4단계에서 3카메라를 시도해 부하·측방 검출의 효용·소비자 연결을 평가한다.
부하가 크거나 측방 소비가 준비되지 않으면 전방만 사용하는 선택을 남긴다.
측방 box를 전방 `/YOLO/BBox`에 섞어 넣지 않는다.
현재 YOLO 설정은 `views: [front]`다. 세 모델의 사용자 실시간 화면 확인은 완료했지만
동시 실행의 처리율·지연·GPU 부하 수락 시험은 후순위다. Batch는 같은 모델의 여러 영상 처리,
공유 runtime은 모델별 전처리·추론을 유지하면서 공통 영상·GPU 자원을 공유하는 실험으로 구분한다.

YOLO 20Hz와 18Hz 이상 수락 조건은 기존 동작 보존을 위한 2단계 기준이다.
대회 주기를 영구 고정하는 조건은 아니다. 4단계에서는 10Hz도 독립 프로필로 비교한다.

현재 fusion의 두 시간 설정은 의미가 다르다.

- `fusion_max_time_offset_sec=0.05`: LiDAR와 YOLO 원본 stamp의 허용 차이.
- `fusion_sync_wait_timeout_sec=0.20`: 지연 도착하는 YOLO 결과를 기다리는 시간.

50ms는 모델이 추론을 50ms 안에 끝내야 한다는 조건이 아니다. 이상적으로 등간격인
10Hz 영상 중 최근접 frame까지의 시간 차이는 최대 50ms지만, 현재 구현은 한 YOLO 결과를
한 LiDAR frame에 사용한 뒤 큐에서 제거한다. 따라서 YOLO가 10Hz, LiDAR가 11–13Hz이면
긴 구간의 고유 YOLO 매칭률 상한은 이상적인 조건에서도 약 77–91%다.
허용 stamp 차이만 확대해 이 공급량 차이를 해결할 수 없다. 이 상한은 모든 LiDAR frame을
fusion에 넘기는 현재 구조의 설명이며 LiDAR 11–13Hz 유지가 대회 필수라는 의미는 아니다.

**LiDAR도 10Hz로 선택하고 YOLO 10Hz와 연결하는 대안**을 4단계의 주요 비교 후보로 둔다.
주기를 조절하는 위치는 다음처럼 구분한다.

- planning 발행만 10Hz: 전달 주기는 줄지만 검출·추적 연산과 fusion 입력 수는 그대로다.
- fusion 입력을 10Hz로 선택: YOLO와 공급량을 맞출 수 있고 LiDAR 검출·추적은 원래 주기로 유지할 수 있다.
- LiDAR 처리 전 최신 완성 scan을 10Hz로 선택: CPU 비용까지 줄일 수 있지만 추적·속도·확인 횟수의
  회귀 검증이 추가로 필요하다. UDP 수신과 scan 조립은 유지해 완성 scan 단위로 선택한다.

두 노드에 각각 `Rate(10)`만 적용해 원본 관측 시각까지 맞춰지는 것은 아니다.
공통 100ms 시간 구간과 원본 stamp 기반 선택을 후보로 검토하고, 먼저 50ms 조건을 유지해 시험한다.
선택한 LiDAR·YOLO의 원본 stamp와 실제 처리 간격을 유지하며, 빠진 주기에 이전 결과를 다시 발행하거나
발행 시각으로 source stamp를 바꿔 안정적인 10Hz처럼 보이게 하지 않는다.
검출·추적을 10Hz로 낮추는 경우 실제 source 간격의 dt와 프레임 수 기반 임계값도 함께 감사한다.

10Hz 대안은 GPU 비용뿐 아니라 매칭 누락, 시간 차이에 따른 투영 오차·오분류,
track 분류 유지·unknown 전환·장애물 반응 시간을 함께 평가한다. 재사용·보간·시간 보정이나
분류 갱신과 LiDAR geometry 출력의 분리는 소비자 정책을 바꾸는 별도 후보로 검토한다.
같은 오래된 검출을 복제 발행해 출력 Hz를 높이는 방식은 사용하지 않는다.

## 1단계 상세 계획

**현재 진행:** 사용자 #65 병합, 로컬 main 갱신, 동일성·validator 검사와 main CI 확인이 완료됐다.
최신 main에 별도 merge나 재복원 작업은 필요하지 않다. 아래 상세 계획은 1단계 범위의 기록으로
유지하고, 2단계는 승인된 P2a 계획에 따라 구현·검증한다.

### 목표와 변경 범위

최신 HD맵 main에 이미 사용자 실행 확인을 마친 카메라 rename을 복원하고 이후 작업의
코드·모델·계약·환경 기준을 확정한다. 이 단계의 변경은 #65 최신 main 반영과 충돌 해결,
검증 기록·계획 문서로 제한한다. 동적 활성화·예열 횟수·모델·뷰 수·추론 Hz·fusion 시간 정책은
2단계 이후에 변경한다. 새 ROS topic·message·activation launch 인자도 이 단계에서 추가하지 않는다.

### 작업 순서

1. 원격 main과 #65의 최신 SHA·CI를 확인한다. verify worktree와 P2 worktree의
   branch/HEAD, 미커밋 파일 목록·SHA를 기록한다. P2를 reset·clean하거나 임의 stash하지 않는다.
2. `verify/asmc-camera-rename`에 최신 `origin/main`을 merge해 공개 PR의 기존 커밋을 유지한다.
   최신 HD맵·지도·규정·pins를 보존하면서 카메라 rename 의도를 함께 적용한다.
   공통 문서는 양쪽의 유효 내용을 통합하고 전체 ours/theirs 선택으로 덮지 않는다.
3. P2 메시지 필드나 검출 라이브러리가 복원 PR에 섞이지 않았는지 확인한다.
   최신 main 대비 `src/asmc_hd_map`, 지도·HD runtime pins와 `src/asmc_msgs`의 내용을
   비교해 복원에 불필요한 변화가 없음을 기록한다. 카메라 파일·모델·설정도 기존 검증 HEAD와 비교한다.
4. 전용 검증 컨테이너에서 submodule·TwinLite 경로·모델 SHA를 확인하고 전체 catkin 및
   nested Msg를 빌드한다. 계약 validator와 카메라·메시지·HD맵·lane adapter 회귀를 실행한다.
5. 기존 bag/live 증거는 당시 SHA의 이력으로 유지한다. 최신 merge의 검사 결과를 별도 기록하며,
   카메라 runtime이 같으면 09-21 bag의 44–86초를 1배속으로 짧게 확인한다.
   runtime에 영향을 주는 충돌 수정이 생기면 해당 기능의 bag 검증을 확대하고 실시간 재확인을 요청한다.
6. 변경된 #65 HEAD를 push하고 CI 3개 결과를 확인한다. 사용자에게 비교 범위와 검증 결과를
   전달하며 최종 merge는 사용자가 수행한다. 병합 후 실제 main SHA를 다음 단계 기준으로 기록한다.
7. P2의 미커밋 변경을 보존한 채 새 main에 옮기는 절차는 2단계 상세 계획에서 정한다.
   1단계 중 기존 P2 브랜치·파일을 이동하거나 수정하지 않는다.

### 검증과 수락

- 최신 main의 HD 코드·지도·pins·규정 메타데이터와 메시지 정의가 보존돼야 한다.
- 전체 빌드, validator와 변경 HEAD의 필수 CI가 통과해야 한다.
- `traffic_light` launch 기본값을 다루는 알려진 facade 실패는 기존 기준선과 비교해 별도 기록한다.
  다른 실패 또는 실패 양상의 변화는 신규 문제로 처리한다.
- 짧은 bag 확인에서는 source stamp 전파, 세 입력 뷰와 camera4, BEV·신호등 결과,
  노드 오류·중복 생산자를 확인한다. 앞선 사용자 수동 운전 성공을 동적 활성화·10Hz 동시 추론의
  성공 증거로 사용하지 않는다.
- P2 미커밋 파일의 SHA가 작업 전후 같아야 한다.
- 실행 안내는 직접 `roslaunch <패키지> <파일> ...`로 제공한다. 사용자가 컨테이너와 bridge를

- #65가 사용자에 의해 병합돼야 1단계 완료다. 이후 2단계 계획을 확정한다.

## 보넷 mask 이후 개발 순서 (2026-10-07)

아래는 사용자 예외 승인 전의 초기 평가·제안 기록이다. 이후 semantic GT 윤곽 mask가
기본 ON으로 선정됐고 기존 보행자 1건만 명시적으로 승인했다. PR #69는 병합 완료이며
현재 상태는 `camera-inference-control.md`, 새 실험은 `camera-lidar-b0.md`를 따른다.

PR #69에 YOLO 전용 mask·동일 설정 overlay·CPU/ROS 시험·독립 MORAI BBox2D 평가를
추가했다. 원본 좌표·메시지·21% crop 어댑터 기본값은 유지한다. 21% 직사각형,
보넷 윤곽, 더 좁은 윤곽을 동일한 정답 목록으로 평가했으며 모두 실제 객체 신규 누락이
있어 **당시 기본 활성화를 보류**했다. 당시 윤곽은 선택 옵션이며 634개 보넷 오검출 프레임을
제거했지만 보행자 1건을 놓쳤다. 이 시점의 수락 보류와 PR Draft 기록은 보존한다.
[mask 기준선](../../../config/baselines/perception_camera_hood_mask_v1.yaml)에 실패를 포함한다.

1. mask 반례의 원인을 확인하고 고정 정답 목록에서 실제 객체 신규 누락 0을 만족한
   후보만 기본 true로 승격한다. 구간별 준비 수락의 준비 p99·첫 1초·지속 10Hz·입력 중단·
   재진입·음영 복귀를 마무리한다. 차선 소비는 음영구간으로 제한하며 판제가 결정한다.
2. 세 모델 동시 부하, 전방/3카메라 YOLO, LiDAR/YOLO 10Hz 조합을 별도 프로필로 비교한다.
   정확도·지연·누락·fusion 결과로 조합을 선정하며 현재 50ms/200ms 정책은 자동 변경하지 않는다.
3. 선정한 mask/입력 조합을 고정해 YOLO26s/m을 비교한다. YOLO11m과 weight는 롤백용으로 보존한다.
4. 측정한 병목에 맞춰 해상도·FP16·같은 모델 batch·공통 전방 디코딩을 각각 독립 비교한다.
5. 모델별 TensorRT의 출력 차이·지연·메모리·fallback을 확인한 뒤 동시 실행한다.
6. RTX 4070 SUPER에서 예열·동시 부하·장시간 안정성을 인수한다.

주행 실험·판제의 jamming/crop 통합은 카메라 mask 검증과 구분하며 카메라 패키지가
구간이나 제어권을 소유하지 않는다. 검증을 통과한 변경만 PR 리뷰 대상으로 전환한다.

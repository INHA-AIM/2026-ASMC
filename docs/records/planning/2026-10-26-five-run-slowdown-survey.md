# 5회 시나리오 감속 원인 조사

**결론: 최고속도보다 재밍 복귀 실패와 장기 정차를 먼저 해결해야 한다.** 실제 주행 5회와
bag 약 12.79GB를 확보했다. 3회는 재밍 출구에서 정지, 1회는 유모차 앞에서 정지,
1회는 출발점에 복귀했지만 CP14를 놓쳤다. 정상 완주 5회의 평균 비교는 아니다.
운영 속도는 올리지 않았다.

## 조사 목적과 조건

사용자 요청: 시나리오를 약 5회 새로 로드하고 주행 bag을 비교해, 전체 평균 속도를
낮추는 과한 감속 구간을 찾는다. 이번 작업은 원인 조사이며 운영 주행 설정을 바꾸지 않는다.
최고 59 km/h 이하, 충돌·차선 이탈·정지선 위반 없이 평균을 개선한다는 기존 목표를 유지한다.

- 기준: `bda91d7a`, `feature/yuntae-speed-59-validation` 작업 트리.
- 운영 launch: `autonomy_no_bridges_v2.launch lidar_source_policy:=asmc_lidar`.
- seed 42, 43, 44, 45 이후 46은 준비 단계에서 두 번, 47은 한 번 실패했다.
  준비 실패 기록도 보존하고 seed 42를 반복해 다섯 번째 실제 주행을 수행한다.
  따라서 서로 다른 seed 5개가 아니라 4개 seed의 주행 5회 비교다.
- 자연 신호 주기를 사용한다. 시나리오의 물체·날씨·시간 변화도 유지한다.
  seed가 같아도 자연 신호의 시작 위상과 센서 타이밍까지 고정되는 것은 아니다.
- 기존 수동 정적 물체 ID `2`는 새 시나리오와 겹치지 않도록 매 회차 x 방향으로 30m
  임시 이동하고 종료 시 원래 위치로 복구한다. 삭제하지 않는다.
  따라서 이전 속도 시험의 장면과 조건이 달라 평균을 직접 전후 비교하지 않는다.
- 기존 브릿지·카메라·LiDAR는 유지하며, 회차별로 소유한 planner·recorder·생성 물체만 정리한다.
- 운영 코드/속도 YAML 및 기존 `lidar+sensorfusion`은 변경하지 않는다. 커밋·푸시·PR 없음.

## 확인된 원인과 다음 검토

### 재밍 출구의 일반 주행 복귀 실패

seed 42, 43, 42 반복에서 약 2001.5m 지점에 정지했다. NORMAL 모드로 돌아온 뒤 KEEP 목표는
57.5 km/h지만 피드백이 `low-speed KEEP blocked by drivable-road boundary`를 반복한다.
앞차나 정지선 대기가 아니며, planner 로그의 횡방향 위치는 기준 경로에서 약 3.7m 벗어나 있다.

복귀 직후의 순서도 중요하다. 세 회차(42, 43, 45) 모두 처음에는
`ego/object input is not fresh`와 브레이크 1.0이 나타난다. 일반 경로가 잠깐 만들어진 뒤
조향 변화율 검사 실패가 발생하며, 42/43은 도로 경계 실패와 장기 정지로 이어지고
45는 경로 생성이 회복돼 계속 주행한다. 복귀 직후 위치 추정과 실제 위치의 차이는
각각 약 14.0m, 8.0m, 5.6m이고 약 2초 뒤에는 0.1~0.2m 수준으로 줄어든다.
측정 시각 차이가 작은 실제 상태와 대조한 값이며 `handoff-evidence.json`에 보존한다.
42 반복도 초기 약 2.6m의 오차와 동일한 장기 정지가 있었다. 오차 크기 하나만으로
실패 여부가 결정된다는 결론은 낼 수 없다.
정상 입력·위치 추정의 준비와 제어 전환을 함께 점검해야 한다. 장애물 위치만으로
성공/실패가 결정된다고 단정하지 않는다.

정지 위치를 현재 raster 지도 검사 방식으로 다시 계산하면 차체 샘플 300개가 모두
주행 가능 영역 밖이다. 반면 시뮬레이터의 실제 포장 도로 mesh 판정은 도로 안이다.
**물리적인 포장 도로와 planner의 허용 영역은 같은 뜻이 아니다.** 이것만으로 지도가 틀렸다거나
허용 영역을 넓혀도 된다고 결론 내리지 않는다. 재밍 종료 차선·자세, 일반 경로 복귀 시점,
허용 영역과 연결 경로를 함께 점검해야 한다. 도로 검사를 끄는 수정은 해결책이 아니다.

관련 구현: `Frenet/Maneuver/Keep.cpp`의 `PlanExternalKeepLowSpeedFallback`,
`Frenet/frenet_planner.cpp`의 `PlanCurvatureFeasibleKeepLowSpeedFallback`,
`Frenet/Map/AvoidRoadMap.cpp`의 raster 차체 검사.

### 재밍 안의 5 km/h 유지

`approaching_unresolved_far_obstacle` 상태에서 저속이 이어진다. 현재 카메라 제어는
장애물 거리를 직접 사용하지 않고, 차선 내 장애물과 옆 차선의 상태를 확인하면서 5 km/h로 제한한다.
해당 진단 상태는 재밍까지 도달한 네 회차에서 각각 18.37, 12.49, 4.34, 16.97초였다.
이 상태에는 감속 중인 시간도 포함된다. 실제 속도 3~6 km/h인 재밍 시간은
각각 12.98, 7.33, 0.78, 12.06초다.
상한부터 올리지 말고 장애물 위치 확인과 안전한 차선 변경 판단이 늦어지는지 살펴볼 대상이다.
`camera_bbox_lane_change_node.cpp`의 `far_obstacle_speed`와 관련 진단이 근거다.

### 유모차 위치의 보행자 보호 정차

seed 44의 시나리오는 교차로에 정적 `BabyStroller1`을 배치한다(s=327m, d=+0.95m).
313m 부근에서 보행자 위험 EMERGENCY가 지속되고, 실제 신호와 감지 신호가 모두 초록일 때도 멈춘다.
원본 bag에서 해당 위치의 LiDAR 융합 객체는 `camera_class=person`, `classification=dynamic_obstacle`,
계획 입력은 `type=2`, `LOW_THREAT`, 속도 0으로 확인된다.
정지 약 207초 중 실제 신호와 감지 신호가 모두 초록인 정지 시간도 약 78초다.
보행자 횡단 NPC는 다른 구간에 있다. 상세 스냅샷은 해당 회차의
`pedestrian-hold-snapshot.json`, `pedestrian-lidar-classification.json`에 보존했다.

이는 실제 사람을 무시해도 된다는 뜻이 아니다. 시나리오의 정적 배치 의도와 카메라 분류,
보행자 보호 및 합법적인 회피 정책의 연결을 점검해야 한다. 검토 전까지 필요한 보호 정지로 분류한다.

### 직선·곡선 및 신호 접근

직선에서는 기존 설정대로 약 57 km/h에 도달한다. 일부 곡선·진출 구간의 속도 하락은
planner의 곡률 제한과 미리 감속하는 속도 프로파일에 대응한다. 신호 접근은 25 km/h 제한을 쓴다.
1·2·4회차의 1560~1630m 최저속도는 약 35.7~36.6 km/h다. 5회차는 이 부근에서
앞차 추종·회피·충돌 차단이 섞이고 순간 최저가 약 0.03 km/h까지 낮아졌다.
따라서 이 회차의 급감속을 곡률 설정 때문이라고 단정할 수 없고, 객체 입력과 명령 전환을
함께 확인할 추가 후보로 남긴다. 0.36 km/h 미만 상태는 0.5초 미만이어서 장기 정지 목록에는 없다.
이 속도 차이만으로 과한 감속이라고 확정할 수 없다. 재밍 복귀와 장기 정차를 해결한 다음,
같은 조건의 완주 기록으로 곡선 추종·정지거리 여유를 확인하며 별도로 조정해야 한다.

## 재현

브릿지와 perception이 실행 중이고 다른 planner가 없는 컨테이너에서 실행한다.
출력 폴더는 새 이름이어야 한다. `--park-static`은 현재 장면에 실제로 있는 수동 물체를
확인한 경우에만 같은 방식으로 사용한다.

```bash
source /opt/ros/noetic/setup.bash
source /root/ws/devel/setup.bash
cd /root/ws/tools/scen_runner
python3 run_slowdown_survey.py \
  --host host.docker.internal \
  --physical-road .runtime/clock-fix-20261022/full-route-road-oracle.json \
  --output /data/derived/slowdown-survey-새로운이름 \
  --seeds 42 43 44 45 46 --deadline 650 --park-static 2:30:0
python3 analyze_slowdown_survey.py /data/derived/slowdown-survey-새로운이름
```

이번 중단 판단은 관찰자가 원인을 확인한 후 수행했다. batch 도구 자체는 같은 정지를
자동으로 조기에 종료하지 않으며, 다시 실행하면 회차별 deadline까지 기다릴 수 있다.
원본 bag과 runtime 지도·모델·로컬 설정은 Git에 넣지 않는다.

## 후속 작업: 재밍 출구 수정

위 5회는 수정 전 조사 기록이다. 이후 사용자의 재밍 출구 수정 요청으로 다음 운영 변경을
진행했다. 속도 설정, raster 허용 영역, 충돌·조향 검사, CP14 통과 반경은 바꾸지 않는다.

1. `planning_inputs`는 GPS invalid 또는 timeout보다 긴 단절 후 옛 속도 기준을 버린다.
   IMU 시각에 맞춘 새 GPS로 위치를 다시 맞추며 새 GPS 속도 기준이 준비될 때까지 invalid다.
   단절 전 누적된 위치를 gain 0.35로 천천히 보정하면서 valid로 내보내던 문제를 막는다.
2. 통합 재밍 카메라 제어는 회피 후 진입 차로로 복귀할 수 있다. 기존 4초 cooldown,
   양 차로 1초 연속 미검출·서로 다른 3 frame, 유효 목표 차로와 차체 경계 내 경로가 필요하다.
   복귀 중에는 BBOX 유실·목표 장애물 검사를 생략하지 않는다. standalone은 opt-in이다.
3. GPS가 돌아와도 일반 주행으로 즉시 넘기지 않는다. 복귀 이후 생성된 150ms 이내 신규

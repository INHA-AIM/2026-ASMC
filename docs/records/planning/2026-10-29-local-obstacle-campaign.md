# LOCAL-2G — 정적 회피·동적 횡단·차체 여유 대조

LOCAL-2F `775c5bb0` 위에서 진행한 GPS 독립 LOCAL 실험이다. 일반 판제와 기존
`jamming_planner:=camera` 기본 선택, 공용 객체 메시지·MD5, LiDAR 검출/추적/fusion,
카메라 학습 모델을 변경하지 않는다. 다른 localization worktree의 소스·프로세스는
변경하지 않았다. 결과는 거리 도달, 물리 여유, 공급 수락을 각각 구분한다.

[ASMC 전체 검수](http://localhost:8000/local2g-20261029-validation01/status.html)에
준비 오류를 포함한 모든 시도, 원본 bag, 실제 명령, native 비교, RGB 재투영을 연결한다.
이전 [LOCAL-2F 기록](2026-10-29-local-braking-recovery.md)은 당시 결과로 보존한다.

않았다. 관측 기반 home은 우측 본차로의 선호 기준이며 물리적 벽 경계가 아니다.

## 의미 그룹과 실제 운동

vehicle/dynamic_obstacle은 물리적 이동을 뜻하지 않는다. 정지한 person은 자차의
이동을 제거한 관측이 정지하면 미래 sweep을 생성하지 않는다. 반대로 static_obstacle
이름이어도 실제로 일관되게 이동한 box는 예측한다. 원래 KF 속도·8코너·ID를 덮지 않는다.

이력은 ID 최대64개·각8관측·0.6초로 제한한다. 최소4개·200ms를 만족하는 가장 짧은
인과 창을 선택해, 정지 이력이 새 이동의 fit에 오래 섞이지 않도록 했다. 최소4관측/0.2초, 강체 형상 변화,
선형 잔차·방향 일관성·실제 변위를 함께 확인한다. 같은 scan 재사용은 확인 횟수를
늘리지 않는다. 현재 측정 OBB가 직전 확인한 운동과 일치할 때만 최대200ms 동안
최근 운동 근거를 보수적으로 유지하며 확인 시각을 갱신하지 않는다. 정지 관측이 쌓이면 예측을 해제해 우회할 수 있게 한다. 이 값들은
일반화된 운동 추정 정확도의 보장이 아닌 이번 후보의 명시적인 한계다.

지금의 미래 hull은 제한된 시간의 합집합을 보수적으로 검사한다. 시공간 경로 탐색이나
확률적 보행자 행동 예측이 아니다. 움직이는 동안 정지/대기와 정지 후 우회를 실제
시나리오로 따로 검사한다. 원래 측정 OBB와 예측 영역은 웹에서 다른 색으로 표시한다.

## 경로·속도 모델

차체 폭2.160835m, 길이4.635m, 후륜축 뒤0.790m를 유지한다. VehicleSpec 폭1.892m로
줄여 통과시키지 않았다. SDK bbox와 실제 접촉 mesh가 같다는 인증도 하지 않는다.

축거3m·조향 gain0.844·최대 곡률0.23/m·조향 변화1rad/s를 유지한다. 최대 조향40도
근처의 물리 한계를 임의로 늘리지 않는다. 과거 저속 후보를 가상1m/s에서 검사하던
보수성을 분리하고, 곡률의 공간 변화율에서 허용 속도를 계산한다.

`delta=atan(L*k/gain)`의 구간 최대 미분을 사용하며, 곡률 부호가 바뀔 때0을 포함한다.
속도 궤적은 기존 jerk/가속도 적분을 유지한다. 현재 속도를 즉시 cap으로 잘라 조향
검사를 통과시키지 않는다. 실제 초기 상태로 slew를 만족하지 못하면 후보가 무효다.
50ms 시간 표본의 조향 변화, 직선 무추가 감속, 가속 중 비실현 cap 반례를 native로 검사한다.

쾌적 감속2m/s²와 controlled3m/s²를 LOCAL 후보에서 대조한다. 일반 플래너의 감속
기본값은 바꾸지 않았다. YOLO 검출 자체로5km/h를 강제하지 않으며, 실제 경로·곡률·
조향 변화·제동 공간이 속도를 제한한다. 회복 경로는 최대3km/h다.

정지 전 미완성 prefix가 물체에 바짝 접근해 다음 우회에 필요한 공간을 없애는 현상도
기록했다. `maneuver_reserve_m`는 이 접근 길이를 줄일 뿐, 충돌 검사를 완화하거나
경로를 관측 밖으로 연장하지 않는다. 객체 뒤까지 통과하는 정상 우회 경로는 줄이지 않는다.

## 시험·접촉 근거의 한계

자동시험은 worktree 전용 master와 전용 센서/인지/제어를 사용했다. MORAI·UDP·GPU는
공유 자원이므로 physical lease와 포트 검사를 통과한 회차만 시작한다. 사용자 공용
11311의 다른 프로세스를 종료해 준비 성공으로 만들지 않는다.

실제 접촉 뒤 MORAI가 삭제된 객체 ID와 `-100`을 계속 보내는 현상을 확인했다.
시작 전에 존재하고 차체가 멀리 있는 ID는 raw evidence로 보존하며 새 접촉으로 세지
않는다. 목록에서 해제돼야 다시 새 사건으로 판정한다. 가까운 시작 접촉은 무시하지
않고 시험을 중단한다. 짧게 나타났다 사라지는 UDP 사건도 보존한다.

이 상태에서 후속 접촉이 완전히 관측된다고 보장할 수 없다. 따라서 별도의 **평가용**
SDK 8코너 hull과 차체의 겹침 guard를 사용했다. 이 GT는 planner/controller의 입력이
아니다. native box 겹침은 mesh 접촉 확정과 구분하며, stale telemetry의 한계 때문에
거리 도달만으로 충돌 무결성 인증을 선언하지 않는다. SetPhysics off/on 확인1회로도
마커가 사라지지 않아 물리 설정을 복구하고 원본 수신을 보존했다.

## 자동 실험의 고정 웹 주소

**http://localhost:8088/web/index_v2.html**을 열면 된다. 별도 ROS master나 autonomy를
시작하지 않는다. 통합 시험의 `dashboard:=false`는 이중 서버를 피하려고 유지하며,
시험기가 같은 master의 기존 dashboard observer를 별도로 한 번 시작한다. LOCAL
단독 경로에도 같은 observer를 붙인다. ROS 처리·제어 노드는 추가하지 않았다.

작은 HTTP 입구는 worktree별로 유지되고 실제 관측 backend는 시험이 소유한다.
run UUID·PID 시작 식별·master와 backend 응답 identity를 검사하며, heartbeat3초
만료·시험 종료·재시작 때 현재 기하를 비운다. 다른 run의 늦은 상세 응답도 거부한다.
32개 작은 plan→source stamp 인덱스로 동시 갱신 때에도 정확한 노면을 읽는다.
이를 새 계획/센서 freshness로 재발행하지 않는다. 종료된 동일 worktree의 입구만
수동 dashboard 시작 시 반환하고, 진행 중 시험·다른 worktree 포트는 보존한다.

실제 drive75 통합→drive76 LOCAL 단독에서 master가11348→11413으로 바뀌어도
같은8088 탭이 연결됐다. 주행 중 새로고침, 종료 후 빈 기하, 다음 run, 한국어와
브라우저 오류0을 확인했다. 이후 drive80에서는 다음 계획이 도착한 뒤에도 이전에
선택한 plan의 정확한 source raster를 조회했다. `monitor-browser03/browser.json`,
`monitor-browser04/browser.json`, `monitor-master-match01.json`이 근거다.

브라우저 검수와 별도 API 확인을 함께 수행한 drive75에서 관측 frontend/backend의
RSS 최대는 약27/55MiB, 평균 CPU는 각각 한 core의6.8/11.4%였다. HTTP는 약141MB,
backend 조회/파싱 평균4.03ms였다. 이 시간은 planner critical path가 아니다.
브라우저를 대부분 닫은 drive76의 같은 observer는 약0.35/3.4%였다. 서로 다른 장면의
비교이므로 동일 입력 OFF/ON 인과 비용으로 해석하지 않는다. 이전 observer metrics의
errors에는 준비 중 접속 대기와 source 갱신409도 섞였다. 이후에는 scene_conflicts를
분리했다. 후보 계산 p95는 각43.60/42.87ms, 유효 경로 공백은189.08/**303.37ms**로,
화면이 연결됐다는 이유로 공급250ms 기준 통과를 선언하지 않는다.

초기 관측 준비 실패도 보존했다. Docker의 Git2.25 backport가 command-line safe.directory를
허용하지 않아, 이 컨테이너의 정확한 mounted worktree만 global trust에 추가했다.
다른 저장소나 컨테이너 설정은 바꾸지 않았다. 설치용 Python 모듈과 메시지 생성물도
재빌드했고, Ego/Collision UDP가 끊긴 준비 회차는 MORAI의 기존 UDP 연결을 다시 맺은 뒤
재검사했다. IP·포트·네트워크 정본 파일은 변경하지 않았다. SDK getter의 저장 ROS 설정을
실제 UI의 활성 UDP 선택과 혼동하지 않는다.

우회, 클래스와 실제 운동 분리, 물리 slew 속도 상한과 저속 CAN seed 실험, 데이터 인계다.
**미완료:** 앞 정지 후 반복 우회 안정성, 작은 객체 동시 인지 누락, 전체 공급 기준이다.
CAN seed는 내부 시험 profile에만 두며 패키지 기본 활성화하지 않았다. 기본 선택은
camera이고 LOCAL은10km/h의 명시적 시험이다. 운영 정본 승격·push·PR·병합은 하지 않았다.

다음 한 단위는 **앞 정지 물체까지의 접근 위치·검증된 우회 prefix 연속성**이다.
정지 자세에 이미 정책 완충 영역이 겹친 뒤 마진이나 곡률만 반복 조절하지 않는다.
현재 노면·원래 OBB·외곽을 매 프레임 재검사하면서, 물체를 지나기 전 검증한 우회
목표와 prefix가 새 home/가림 때문에 다시 직선 접근으로 대체되는지 분리한다.
Dog와 얇은 물체의 raw 점 지지/군집 탈락/fusion 누락은 인지 보완 단위로 남긴다.

## 미래 조향 구간 검사 보완과 마지막 회귀

공백을 sequence로 추적하니76의303ms 안에는2개의
`initial_steering_slew_infeasible` 결정이 있었다. 이를 센서 단절로 단정하지 않는다.
새 조향 속도 검사에서 경로 전체의 가장 큰 공간 변화율을 현재 속도에 바로 적용하던
보수성이 확인됐다. 실제 시간 적분에서 각50ms에 도달하는 arc 구간만 검사하며,
나중 급한 구간도 그 시점의 실제 속도로 검사한다. 기존 최대 곡률/조향 slew/jerk는 유지한다.
현재 직선에서 감속한 뒤 미래 회전이 가능한 native 반례가 통과했고, 실제로 처음부터
불가능한 급변은 계속 거부한다. MPC 자체가 미래를 예측하는 구조를 약화한 것이 아니다.

추가85·좌측 barrier는60.19m, 계산 p95 43.18ms, 유효 경로 최대 공백138.97ms,
조향 infeasible0회였다. 86·연속 drum은60.16m에 도달했지만 p95 **50.11ms**,
공백 **501.80ms**와 해당 거부5회가 남았다. 서로 다른 센서 입력의 반복이므로
차이를 전부 이번 수정의 효과로 단정하지 않는다. 이번 완료 후의 총량은 **86등록 시도·
native구간59회·거리 목표35회·2,454.15m**다. 공급/계산 전체 수락은 여전히 보류한다.

마지막 C++ 변경은 native 회귀와85/86 실시간으로 추가 검사했다. 전체 planning CI는
그 직전 공통 기준에서 통과했으며, GitHub 원격 CI를 새로 실행한 결과가 아니다.
검수 페이지는 최초84시도 출력과85/86 추가 비교를 따로 보존한다. 기존 run을
재생성하거나 결과를 덮어쓰지 않았다.

# L2-A2 실제 Main·Patchwork++ GT 재검증 (2026-10-04)

상태: **지면 단계 검증 완료, Patchwork++ 운영 미채택**. 이 문서는 기존
[`v3 GT 비교`](./l2a2-dual-gt-ground-review-20261004.md)의 숫자가 실제
손재호 `Main`과 어느 정도 일치하는지 확인하고, 처리시간 해석을 바로잡는다.
최종 객체 검출·추적·판제 주행 성능을 승인하지 않는다.

## 무엇을 직접 실행했나

- 손재호 지면 소스(`RoiVoxel.cpp`, `ImuFusion.cpp`, `Ransac.cpp`)는 고정 기준
  `6435af1`과 현재 worktree `6e50c44` 사이에 diff가 없다. 현재 소스를
  수정하지 않고 `/tmp/asmc_jaeho_runtime_build`에 `Main`을 빌드했다.
  실행 바이너리 SHA-256은 `5a341b8f8ed0d07e671d4eea114badd73dd878e51d7bd8846d0c881b23f46de2`다.
- `--network none`의 독립 ROS master에서 실제 `Main`과 `asmc_lidar` 리뷰 노드를
  raw bag의 마지막 23초에 재생했다. `Main`은 20회 예열·200회 계측 뒤 종료하도록
  설정했다. 216개 `/lidar/debug_roi` 프레임의 점 수가 점별 기준선과 **216/216
  정확히 일치**했다. `/lidar/debug_ransac` 점 수는 원본 인덱스→voxel 계보로
  계산한 기대치와 프레임당 최대 1점 차이다.
- 동기 Sensor Record의 `sync_001050`–`sync_001270` 221프레임은 원본 LiDAR
  XYZI와 같은 stem의 실제 IMU quaternion을 ROS bag으로 재구성했다. 원본
  `nSecs`는 비정규여서 파일명 시각을 header stamp로 쓰고, bag 도착 시각은
  별도 합성값이다. `Main`의 191개 지면 출력은 ROI·RANSAC voxel 점 수 모두
  점별 기준선과 **191/191 정확히 일치**했다. 후보 ROS 노드는 stamp를
  유지하고 bag 도착만 25ms 늦춘 별도 재생에서 221/221 정상 처리했다.
  합성 25ms를 실제 네트워크 지연으로 해석하지 않는다.
- 두 전체 수집본에서 GT semantic·instance와 **원본 인덱스 마스크를 다시
  직접 집계**했다. 이 점별 비율은 실제 ROS debug cloud가 ID를 보존하지
  않으므로, 위 점 수 parity로 실제 실행 경로를 교차검증한 오프라인 결과다.

재생 결과는 `$ASMC_DATA/lidar_assessment/20261004_gt_dual_ground/` 아래
`main_replay_raw/`, `main_replay_sync/`, `candidate_replay_sync/`에 있다.

## 아스팔트 100%의 정확한 의미

100%는 **공통 ROI에 들어온 GT `Asphalt(127)` 원점 중 기준선이 ground로
분류한 비율**이다. 센서가 본 모든 도로나 최종 객체 검출 정확도가 아니다.
`Sidewalk(129)`와 `ETC(10)`도 거의 모두 제거하므로, 아스팔트 제거율만으로
과도 삭제가 없다고 판단할 수 없다. `ETC`는 미확정 라벨이며 삭제가 옳거나
그르다고 자동 판정하지 않는다. 보도 삭제도 점유/경계 용도와 분리해서 봐야 한다.

위 보존/삭제는 **지면 단계의 점 분류**다. 같은 객체가 여러 프레임에 나타나며,
GT `Obstacle(164)`의 객체 box는 별도 검증 제한이 있다. 기준선은 raw ROI
30,395,026점 중 28,865,443점을 ground로 분류했고, 고정 Patchwork++는
26,732,822점을 분류했다. 이 차이를 곧바로 장애물 성능 개선으로 읽으면 안 된다.

GT instance의 10분위 z를 밑면 대용으로 잡으면, 차량 하부 0–20cm 점의
지면 오분류는 raw에서 재호 5.15%, Patchwork++ 42.78%, 동기에서 각각
7.52%, 37.76%다. 재호는 이 분석의 차량 중·상부를 삭제하지 않았지만
하부를 자르는 현상은 있다. Patchwork++는 raw 차량의 20–60cm 구간도
24.81%, 60cm 위도 7.25%를 삭제했다. 이는 수평 차체 면을 지역 지면으로
채택하는 문제와 합치하나, plane별 원인을 확인하기 전에는 단정하지 않는다.

## 실제 처리시간과 한 변수 탐색

실제 `Main`의 내장 계측은 raw 200프레임에서 전체 median **1.861ms**,
p95 3.034ms, RANSAC 평균 0.320ms였다. 동기 180프레임에서는 전체 median
**2.313ms**, p95 3.488ms, RANSAC 평균 0.329ms였다. 이전 오프라인 도구의
voxel 약 20ms는 원본 점 계보 복원을 위한 `setSaveLeafLayout(true)` 등
평가기 비용이며 **현재 Main의 실제 실행시간으로 인용하면 안 된다**.
Patchwork++ 자체 오프라인 분할 p50은 같은 voxel 표현에서 raw 0.578ms,
동기 0.584ms였다. 원본 점에서는 raw 0.757ms, 동기 0.753ms였다.
ROS 후보 리뷰 노드는 기준선+Patchwork++를 함께 계산하고 점군까지 발행해
raw median 16.65ms, 동기 유효 재생 median 18.39ms였으므로, `Main`의
1.86/2.31ms와 직접 속도 우열을 내면 안 된다. 현재 **Patchwork++가 더
빠르다는 증거는 없다**.

탐색 진단 하나로, 원본 점 Patchwork++의 ground 후보 중 pitch 수평화 z가
`-1.45m`보다 높은 점만 보존했다. 이는 센서-노면 높이 1.80m에서 35cm
위까지의 고정 사전값이며 GT를 정책 입력으로 쓰지 않는다. raw/동기 차량
삭제율이 각각 23.21→2.70%, 17.72→2.51%로 내려갔고 아스팔트 제거율은
95.72/96.14% 그대로였다. 그러나 raw 차량 완전 소실은 30→2/249로,
재호 원본 점 대조군 1/249보다 여전히 한 건 많다. 보도 제거도 약 59–60%로
남아 non-ground clutter 문제가 해결되지 않았다. 이 입력을 이미 분석한 뒤의
**동일 자료 탐색**이고 독립 검증·운영 후보가 아니다. 자료와 결과는
`reports/{raw,sync}_height_guard_probe.json`에 남겼다.

소실 추가 0건·보행자/낮은 장애물 보존·아스팔트 잔여/보도 clutter·최종
군집/OBB·CPU 시간을 **같은 입력과 새 홀드아웃**에서 동시에 검사한다.
단일 z 임계값을 운영에 넣거나 현재 판제 입력을 바꾸지 않는다.
